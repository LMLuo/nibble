# 05 · 风险与应对

**定位**：升级过程中会踩的坑与对策，按严重度排序。贯穿"隐私红线、性能边界、留存、发布、维护"。

---

## 风险清单

### R1 · 隐私承诺被打破（严重度：高）
- **风险**：为做"报错=怪物""测试=暴击"等好玩机制，可能 tempted 去读错误内容/代码，违背"绝不读内容"的承诺，损害信任。
- **对策**：
  - 架构级红线（`02` 第八节）：L0 零读取为默认；L1 只读聚合计数/布尔，不读内容；L2 本版不做。
  - 任何 L1 事件在扩展侧处理后**立即丢弃原始数据**，只把聚合值写入 `save.json`。
  - 设置中显式展示"当前权限等级"与开关，用户随时可关。
  - 代码评审强制检查：凡涉及 `diagnostics`/文件读取的模块，必须只取聚合值。

### R2 · 留存不足，升级后仍流失（严重度：高）
- **风险**：机制加了但玩家仍只玩几天。
- **对策**：日常/成就/赛季构成留存引擎（阶段 3/5）；7 日留存目标提升 ≥30%（`00` G5）；用"行为画像进化"制造"养成我的专属宠物"的长期动机。

### R3 · hook 环境受限（Windows Git Bash + Node16）（严重度：中）
- **风险**：重逻辑放 hook 端会卡顿或语法不兼容。
- **对策**：hook 端只 emit 事件 + 轻量落盘；重计算放游戏核心（可在扩展侧或预计算）；严守 Node16 语法；不引入原生依赖。

### R4 · 底部/状态栏 UI 空间有限（严重度：中）
- **风险**：图鉴/任务/装饰等重交互无处安放。
- **对策**：重交互迁至"交互面板（主动打开）"；状态栏只放等级/HP/连击等极简提示；复用现有 24×24 与大图能力。

### R5 · 机制膨胀、复杂度失控（严重度：中）
- **风险**：一次加太多机制，代码与维护成本爆表。
- **对策**：严格按 `04` 阶段 0~5 分期；每机制先登记（`01` 第五节）再实现；核心保持纯逻辑、内容走配置。

### R6 · 平衡性崩坏（严重度：中）
- **风险**：进化/技能/数值失衡，导致某分支过强或无敌。
- **对策**：数值集中在 `rules/*.json`，便于调参；阶段结束做平衡自测；保留"重置"能力（`/nibble reset` 演进为可重置单模块）。

### R7 · 跨平台与发布（严重度：中）
- **风险**：Windows Git Bash 路径/中文、Open VSX 命名空间未认领、`engines.vscode` 写 `*` 静默不加载等既有坑复发。
- **对策**：沿用既有 CI 与发布流程（`PUBLISHING.md`）；不重构发布链路；命名空间认领按 `project_nibble_runtime.md` 既有 issue 跟进。

### R8 · 数据迁移失败丢档（严重度：中）
- **风险**：`save.json` 结构大改导致老用户进度丢失，引发差评。
- **对策**：`schemaVersion` + 迁移脚本（`02` 第三节），缺字段补默认值，迁移失败回退到安全默认值并提示，绝不静默清空。

### R9 · 性能与 token 消耗（严重度：低~中）
- **风险**：频繁事件导致日志刷屏或意外进入模型上下文。
- **对策**：沿用 `systemMessage` + `suppressOutput` 不耗 token；事件去抖（如诊断变化聚合为每秒一次）；保持默认轻量。

### R10 · 社交/赛季需后端，成本与隐私外溢（严重度：中，但可控）
- **风险**：阶段 5 联网功能引入服务器成本与隐私争议。
- **对策**：列为"可选 + 评估项"；优先做本地/匿名轻量榜；任何联网功能显式授权并独立隐私声明；不读内容红线不变。

# Nibble 游戏升级规划 · 文档导航

> 本目录集中存放《Nibble 陪伴小生物》从 v0.1.x 向更完整玩法升级的全部规划与设计文档。
> 所有文档以"可直接作为项目升级方案使用"为目标，按"总览 → 专题深潜 → 执行"的层级组织。

---

## 二、各文档用途说明

| 文档 | 用途 | 主要读者 | 何时看 |
|---|---|---|---|
| `README.md` | 导航与索引；说明目录结构与每份文档的职责；给出推荐阅读顺序 | 所有人 | 任何阶段，先读这一份 |
| `00-游戏升级规划书.md` | **总纲**。一份文档讲清升级目标、方向、机制/系统/内容/阶段/优先级/风险的整体方案，可直接对外汇报或立项 | 决策者、PM、开发者 | 立项、评审、向他人介绍升级方案 |
| `01-核心玩法机制.md` | 玩法设计的"创意库 + 决策依据"。逐条列出可加入的机制、为什么好玩、以及如何组合成完整循环 | 玩法/系统设计师 | 设计玩法、排期机制优先级 |
| `02-可扩展系统架构.md` | 把玩法落到工程上的架构方案；定义数据模型、事件层、渲染层、扩展点、隐私分级 | 开发者、架构师 | 进入开发前、做技术评审 |
| `03-内容规划.md` | 玩法所需的"填充物"清单（可数据驱动维护）：物种、敌人、技能、成就、剧情、皮肤、赛季 | 内容策划、开发者 | 做内容、设计新物种/活动 |
| `04-开发阶段与里程碑.md` | 把总纲拆成可执行的开发阶段，含目标/交付物/退出标准/版本号 | 开发负责人、PM | 排期、迭代规划、进度跟踪 |
| `05-风险与应对.md` | 升级过程中会踩的坑与对策清单，按严重度排序 | 负责人、开发者 | 评审风险、制定缓解计划 |

## 三、推荐阅读顺序

1. **先读总纲**：`00-游戏升级规划书.md` —— 5 分钟建立全局认知。
2. **想清楚"玩什么"**：`01-核心玩法机制.md` → `03-内容规划.md`（机制与内容配对看）。
3. **想清楚"怎么落地"**：`02-可扩展系统架构.md` → `04-开发阶段与里程碑.md`。
4. **规避风险与长期运营**：`05-风险与应对.md` → `06-维护与迭代手册.md`。
5. **动手排期前先看进度**：`12-开发进度盘点与后续路线图.md` —— 它把"规划里写了什么"和"代码里真有什么"并排放，避免重复规划已落地的东西、或漏掉被跳过的地基。

## 四、版本与命名约定

- 本文档随游戏版本演进，文件名中的 `00~11` 为固定序号，**不随版本号变化**，便于长期引用。
- 规划书覆盖的目标基线：`00` 的"现有能力"写于 v0.1.1；**当前线上已落地** Roguelite 战斗 + 跨会话存档 + 武器库（战力/装备）+ 怪物库 + 连击 + 技能书（50 本 / 4 槽 / 以牙还牙等 12 条组合）+ 玩家血量与怪物反击（详见 `07~11`）；升级路线目标版本区间仍为 **v0.2 → v1.0 → v2.0**（详见 `04-开发阶段与里程碑.md`）。
- 涉及游戏数值（攻击力、经验曲线等）以 `01/03` 为设计基线，`02` 落地，最终以代码 `save.json` schema 与配置为准。

## 五、维护提示

- 新增机制：先在 `01` 登记，再在 `03` 补内容表，最后在 `04` 排期。
- 新增风险：同步更新 `05`。
- 每次发版后，在 `06` 记录复盘，并回写受影响章节。
